Tax Form Annotation Spec (v1)

1. The problem

A U.S. tax form — a W-2, a 1099-INT, a 1040 — is a fixed page of labeled boxes. The IRS (or the SSA, for a W-2) defines exactly what each box means and roughly where it sits on the page. A taxpayer's actual numbers live somewhere else entirely: in a database, as deeply nested JSON, shaped however the platform that owns the data wants it shaped.

Two people typically do this work, at different times, without talking to each other:

  • The annotator looks at a blank form and records, per box: where it is, how it should be formatted, and which value it needs.
  • The renderer is a separate application — someone else's code — that takes the annotator's file plus a taxpayer's data and stamps the right value into the right box.

This document defines the file that sits between them: the annotation file. It is pure JSON, so it can be hand-written, generated by a UI, or scripted. It does not define a rendering engine, a PDF library, or any platform's data model — only the contract between "here's a form" and "here's the data."

2. Design goals

  • Positioning — every box knows exactly where it is on the page.
  • Formatting — every box knows how its value should look once printed.
  • Deep data referencing — a box can point at a value buried anywhere inside an arbitrarily nested taxpayer dataset, not just a flat key.
  • Stable field identity — a box's identity survives edits to the form and stays usable as a key by other systems (e.g. an audit trail, a UI that highlights "line 1a").
  • Conditional rendering — a box can be told to only appear when the data warrants it (many form lines are "leave blank if not applicable").
  • Grounded in the real form — positions and labels trace back to the form's official IRS/SSA-published layout for a given tax year, not to guesswork.

3. Top-level structure: FormTemplate

One FormTemplate document describes one form, for one tax year.

{
  "formId": "W-2",
  "formVersion": "2024",
  "title": "Wage and Tax Statement",
  "issuingAgency": "SSA",
  "pages": [
    { "number": 1, "width": 612, "height": 396, "unit": "pt" }
  ],
  "fields": [ /* FieldAnnotation[] — see §4 */ ]
}
Property Type Notes
formId string Stable identifier for the form, e.g. "W-2", "1099-INT", "F1040".
formVersion string Tax year the layout matches, e.g. "2024". IRS forms are revised yearly — this is what lets a renderer pick the right template.
title string Official form title, for display.
issuingAgency string "IRS" or "SSA" — which agency publishes this form's layout.
pages Page[] Physical page geometry — see §5.
fields FieldAnnotation[] One entry per printable box, or per repeating box template — see §4.

4. FieldAnnotation — one per box

{
  "id": "w2.box1.wages",
  "formLine": "Box 1",
  "description": "Wages, tips, other compensation",
  "page": 1,
  "position": { "x": 396, "y": 118, "width": 130, "height": 16, "unit": "pt" },
  "format": {
    "type": "currency",
    "decimalPlaces": 2,
    "alignment": "right",
    "negativeStyle": "parentheses"
  },
  "dataBinding": {
    "path": "$.income.w2Forms[*].box1Wages",
    "aggregate": "sum",
    "fallback": 0
  }
}
Property Type Required Notes
id string yes Unique within the form, stable across formVersion revisions — see §7.
formLine string yes The form's own label for the box (e.g. "Box 1", "1040 Line 1a"), for traceability against the official form.
description string no Longer human-readable explanation, useful when reviewing an annotation.
page integer yes 1-indexed page this box appears on.
position Position yes See §5.
format FormatSpec yes See §6.
dataBinding DataBinding yes* See §7. Omit only for a literal-formatted box (static text) — see §6.4.
conditional ConditionalSpec no See §8. Whether the box renders at all.
repeat RepeatSpec no See §9. Turns one annotation into a template for N repeated rows.

5. Positioning — grounded in the official form

"position": { "x": 396, "y": 118, "width": 130, "height": 16, "unit": "pt" }
  • Units: points (pt, 1/72 inch) internally. in and mm are legal per annotation for authoring convenience, but a renderer normalizes everything to pt before doing layout math (in * 72, mm * 72 / 25.4) — never mix units.
  • Origin: top-left of the page. x increases right, y increases down — matching how a person measures coordinates off a scanned form image or a design tool (Figma, browser CSS, <canvas>), which is how most annotators will actually pull these numbers.
  • Box, not baseline: x, y is the box's top-left corner; width, height is its printable area. A renderer is free to inset padding or vertically center text inside that box — the spec only guarantees the outer rectangle.
  • Source of truth: x, y, width, height are measured directly off the IRS's (or SSA's) own published layout for that formId + formVersion — the official PDF/image, not a redrawn approximation. formLine is likewise copied verbatim from the official form so a reviewer can cross-check every box against the source document. This matters because layouts shift between tax years; re-annotating a new formVersion means re-measuring against that year's official form, not reusing last year's coordinates.

6. Formatting

"format": {
  "type": "currency",
  "decimalPlaces": 2,
  "alignment": "right",
  "negativeStyle": "parentheses"
}
Property Type Applies to Notes
type string all "currency" | "number" | "percent" | "date" | "ssn" | "ein" | "text" | "boolean" | "literal".
decimalPlaces integer currency, number, percent Digits after the decimal point. IRS money boxes are usually 2.
alignment string all "left" | "right" | "center". Numbers are conventionally right-aligned.
negativeStyle string currency, number How a negative resolved value should be printed. "minus" → "-100.00". "parentheses" → "(100.00)", the accounting convention many IRS forms use. "redText" is a renderer hint (no ASCII change) for forms that print negatives in red.
dateFormat string date e.g. "MM/DD/YYYY".
mask string ssn, ein A redaction pattern, e.g. "XXX-XX-####": X prints literally (redacted), # reveals the actual digit at that position (right-aligned against the real value), anything else (like -) prints as-is. Omit for no redaction.
literalValue string literal For type: "literal" boxes with no dataBinding — static form text, not taxpayer data.

7. Data binding — referencing a deeply nested dataset

"dataBinding": {
  "path": "$.income.w2Forms[*].box1Wages",
  "aggregate": "sum",
  "fallback": 0
}
  • path is a JSONPath-lite expression evaluated against the taxpayer's data document (the "values" file). It supports:
    • Dot access into nested objects: $.taxpayer.address.zip
    • Array indexing: $.income.w2Forms[0].box1Wages (first employer's wages)
    • Array wildcards: $.income.w2Forms[*].box1Wages (every employer)
    • Filters: $.income.w2Forms[?(@.isPrimary==true)].box1Wages
  • aggregate collapses a wildcard/filter match down to one printable value: "sum", "first", "count", "min", "max", "join" (for text). Omit it when path already resolves to a single value.
  • fallback is what a renderer should print when the path resolves to nothing (e.g. a taxpayer with no 1099-INT forms) — usually 0, "", or null to mean "leave the box blank."

This is deliberately a small, predictable subset of JSONPath rather than the full grammar — every renderer must implement the same handful of operators the same way, so the same annotation file behaves identically everywhere.

8. Stable field identity

id is required, unique within a FormTemplate, and is expected to stay the same across formVersion revisions of the same formId whenever the underlying box genuinely didn't move meaning (e.g. "w2.box1.wages" should still mean Box 1 wages next year, even if its pixel coordinates shifted slightly). This lets downstream systems — an audit log, a "jump to this line" UI, a diff between two years' annotation files — key off id without caring about layout churn. A convention like "<formId>.<box>.<shortName>" (dot-separated segments, camelCase within a segment) keeps ids both stable and self-describing; the spec doesn't mandate the convention, only the uniqueness and stability guarantees.

9. Conditional rendering

"conditional": {
  "path": "$.income.hasForeignAccount",
  "equals": true
}

A box with a conditional block is only drawn when the condition evaluates true against the taxpayer's data; otherwise the renderer skips it entirely (not "prints blank" — it's not laid out at all). Supported comparisons: equals, notEquals, exists (path resolves to any non-null value), greaterThan / lessThan (for numeric thresholds, e.g. "only show this line if income exceeds $X"). Many real IRS lines are conditional this way — "complete only if you checked box 2" — so this is a core requirement, not an edge case.

10. Repeating rows

"repeat": {
  "sourcePath": "$.income.w2Forms",
  "rowHeight": 18,
  "maxRows": 4
}

Some boxes represent one row in a set that repeats per array item — multiple employers on a summary page, multiple broker transactions on a 1099-B. Rather than hand-writing N near-identical FieldAnnotations, one annotation with a repeat block is a template: the renderer iterates sourcePath, and for the Nth item, offsets that field's position.y by N * rowHeight (or x, if the form repeats horizontally — a direction property defaults to "vertical"). maxRows caps how many rows the physical form has room for; a renderer decides how to handle overflow (a continuation page, a "see attached" note) — that policy is intentionally out of scope for this spec.

11. Form versioning

formVersion exists because IRS/SSA forms are revised yearly and boxes do move, get renumbered, or disappear. A renderer selects the FormTemplate matching both formId and the tax year of the return being printed; annotation files for different years of the same form are separate documents, not diffs against each other. This keeps each FormTemplate self-contained and trivially reviewable against that year's official form.

12. Worked example — W-2, Box 1

Given this annotation:

{
  "id": "w2.box1.wages",
  "formLine": "Box 1",
  "page": 1,
  "position": { "x": 396, "y": 118, "width": 130, "height": 16, "unit": "pt" },
  "format": { "type": "currency", "decimalPlaces": 2, "alignment": "right", "negativeStyle": "parentheses" },
  "dataBinding": { "path": "$.income.w2Forms[*].box1Wages", "aggregate": "sum", "fallback": 0 }
}

...and this taxpayer data:

{ "income": { "w2Forms": [ { "box1Wages": 52340.12 }, { "box1Wages": 8100.00 } ] } }

A resolver combines the two into one print-ready instruction:

{ "id": "w2.box1.wages", "page": 1, "position": { "x": 396, "y": 118, "width": 130, "height": 16, "unit": "pt" }, "value": "60,440.12" }

box1Wages was summed across both W-2s (aggregate: "sum"), formatted as currency with 2 decimals. Every field in a FormTemplate resolves the same way — this is the full W-2 worked out end to end in samples/w2/.

13. Out of scope (for now) / future enhancements

  • Rendering engine — how a box's value actually gets drawn onto a PDF or image is a renderer's job, not this spec's.
  • Multi-value boxes — a box that shows two related numbers side by side (rare, but exists on a few IRS forms) isn't modeled yet; today it needs two FieldAnnotations.
  • Localization — format assumes U.S. conventions ($, MM/DD/YYYY). A locale field on FormTemplate would be the natural extension point.
  • Computed/derived boxes — a box whose value is arithmetic over other boxes on the same form (e.g. a subtotal line) currently needs the platform to precompute it into the values file. A dataBinding.expression (sum of other field ids) is a natural v2 addition.
  • Schema-validated path expressions — today a bad path just resolves to the fallback at runtime. Validating paths against a taxpayer data schema ahead of time (catching typos before print time) is a reasonable v2 addition.
