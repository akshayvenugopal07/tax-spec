# Tax Form Annotation Specification (v1.0)

## 1. Problem

A tax form (1040, W-2, Schedule B, ...) is a fixed visual layout of labeled
boxes. A taxpayer's actual data lives in a deeply nested, arbitrarily shaped
JSON document (a W-2 has an employer, which has wages, which may repeat
across multiple employers, etc.). Two different people typically do this
work at different times:

- **Annotator**: someone who looks at the blank form and records, per box,
  *where it is* and *what value belongs there*.
- **Renderer**: an application, built independently, that takes the
  annotation file plus a taxpayer's data and draws the right value in the
  right box, correctly formatted.

This spec defines the file format that sits between those two people. It
does **not** define the rendering engine, the PDF library, or the data
model of any specific tax platform — only the contract between annotation
and data.

A `FormTemplate` document is the deliverable of the *annotator*. It is pure
data (JSON), so it can be authored by hand, generated by a UI tool, or
produced by a script — the spec doesn't care.

## 2. Top-level structure

```jsonc
{
  "formId": "F1040",
  "formVersion": "2024",
  "title": "U.S. Individual Income Tax Return",
  "pages": [
    { "number": 1, "width": 612, "height": 792, "unit": "pt" }
  ],
  "fields": [ /* FieldAnnotation[] — see §3 */ ]
}
```

| Property      | Type              | Notes                                                          |
|---------------|-------------------|------------------------------------------------------------------|
| `formId`      | string            | Stable identifier for the form, e.g. `"F1040"`, `"W-2"`.        |
| `formVersion` | string            | Tax year or revision, e.g. `"2024"`. Forms change yearly.       |
| `title`       | string            | Human-readable form name.                                       |
| `pages`       | `Page[]`          | Physical page geometry — see §4.                                 |
| `fields`      | `FieldAnnotation[]` | One entry per printable box (or repeating box template).       |

## 3. `FieldAnnotation`

This is the core unit of the spec — one per box on the form.

```jsonc
{
  "id": "line1a",
  "formLine": "1040 Line 1a",
  "description": "Total amount from Form(s) W-2, box 1",
  "page": 1,
  "position": { "x": 468, "y": 214, "width": 92, "height": 14, "unit": "pt" },
  "format": {
    "type": "currency",
    "decimalPlaces": 0,
    "alignment": "right",
    "negativeStyle": "parentheses"
  },
  "dataBinding": {
    "path": "$.income.w2Forms[*].box1Wages",
    "aggregate": "sum",
    "fallback": 0
  }
}
```

| Property      | Type            | Required | Notes                                                                 |
|---------------|-----------------|----------|-------------------------------------------------------------------------|
| `id`          | string          | yes      | Unique within the form. Stable across versions if possible — renderers and downstream tools key off it. |
| `formLine`    | string          | yes      | The form's own label for the box (what a human would call it), for traceability/debugging. |
| `description` | string          | no       | Longer explanation, useful for annotators reviewing their own work.     |
| `page`        | integer         | yes      | 1-indexed page this box appears on.                                     |
| `position`    | `Position`      | yes      | See §4.                                                                  |
| `format`      | `FormatSpec`    | yes      | See §5.                                                                  |
| `dataBinding` | `DataBinding`   | yes*     | See §6. Omit only for `computed`/static-label boxes (rare; use `literal` instead — §6.4). |
| `conditional` | `ConditionalSpec` | no     | See §7. Whether to render the box at all.                               |
| `repeat`      | `RepeatSpec`    | no       | See §8. Turns one annotation into a template for N repeated rows.       |

## 4. Positioning

```jsonc
"position": { "x": 468, "y": 214, "width": 92, "height": 14, "unit": "pt" }
```

- **Units**: points (`pt`, 1/72 inch) by default. `in` and `mm` are also
  legal per-annotation for authoring convenience, but a renderer should
  normalize everything to `pt` internally (`in * 72`, `mm * 72 / 25.4`)
  before laying out — never mix units in downstream math.
- **Origin**: **top-left** of the page, x increasing right, y increasing
  **down** — matching how a human looking at a scanned form image or design
  tool (Figma, browser CSS, `<canvas>`) naturally measures coordinates, and
  how most annotators will pull numbers (e.g. from a PDF-to-image overlay
  tool). This is the annotation-authoring convention.
- **Box, not baseline**: `x, y` is the box's top-left corner; `width,
  height` is its bounding box, not a text baseline. This lets renderers
  center/right-align/vertically-center text inside the box using `format`
  rather than the annotator hand-computing a baseline offset.
- **PDF coordinate note**: PDF's native coordinate space has the origin at
  the page's **bottom-left**, y increasing up. A renderer drawing onto a
  PDF must convert:
  `pdfY = pageHeight - position.y - position.height` (for the box's bottom
  edge) before calling a PDF library's text-drawing primitive. This
  conversion is a renderer concern, not an annotation concern — annotators
  never need to think in PDF space.
- **Page**: `pages[]` in the top-level document declares each page's size
  so a renderer/validator can catch out-of-bounds boxes without opening the
  actual form asset.

## 5. `FormatSpec`

Governs how a resolved raw value becomes the text actually drawn in the box.

| Property        | Type      | Applies to        | Notes                                                                 |
|------------------|-----------|--------------------|-------------------------------------------------------------------------|
| `type`           | enum      | all                | `currency`, `number`, `integer`, `percent`, `text`, `date`, `ssn`, `ein`, `phone`, `checkbox`, `signature`. Drives default formatting rules below. |
| `decimalPlaces`  | integer   | currency/number/percent | Default: `2` for currency/percent, `0` for integer.              |
| `negativeStyle`  | enum      | currency/number    | `"parentheses"` (tax-form convention, e.g. `(1,204)`), `"minus"`, or `"none"` (assumes value pre-signed/unsigned). Default `"minus"`. |
| `alignment`      | enum      | all                | `"left"`, `"center"`, `"right"`. Default: `right` for numeric types, `left` for text/date, `center` for checkbox. |
| `thousandsSeparator` | boolean | currency/number  | Default `true`.                                                        |
| `font`           | object    | all                | `{ family?, size?, weight? }` — hints only; a renderer may substitute its own font as long as it fits the box (see `overflow`). |
| `maxLength`      | integer   | text/ssn/ein/phone | Hard cap; renderer should treat as a validation signal from the annotator, not silently truncate without applying `overflow`. |
| `textTransform`  | enum      | text               | `"uppercase" \| "none"`.                                               |
| `dateFormat`     | string    | date               | e.g. `"MM/DD/YYYY"`. Uses standard strftime-style tokens.              |
| `checkboxMark`   | enum      | checkbox           | `"X" \| "check"` — what to draw when the bound boolean is `true`. Nothing is drawn when `false`. |
| `overflow`       | enum      | all                | `"shrink-to-fit"` (reduce font size until it fits, down to a reasonable floor), `"wrap"`, `"truncate"`, `"error"` (renderer should flag, not silently mangle). Default `"shrink-to-fit"`. |

`ssn` / `ein` / `phone` are masking presets (`"###-##-####"`,
`"##-#######"`, `"(###) ###-####"`) applied to the raw digit string — kept
as their own `type` values rather than a generic mask string so common tax
identifiers are correct by default without every annotator re-deriving the
punctuation.

## 6. `DataBinding` — referencing a value in deeply nested data

This is the piece that connects a box to *where its value lives* inside an
arbitrarily nested taxpayer data document. It's a small JSONPath-flavored
language — enough to reach into nested objects, iterate arrays, filter, and
aggregate, without building a full expression/formula engine (kept
intentionally out of scope — see §11).

```jsonc
"dataBinding": {
  "path": "$.income.w2Forms[?(@.employerState=='CA')].box1Wages",
  "aggregate": "sum",
  "transform": "round",
  "fallback": 0
}
```

| Property    | Type    | Required | Notes                                                                    |
|-------------|---------|----------|----------------------------------------------------------------------------|
| `path`      | string  | yes**    | JSONPath-lite expression, evaluated against the taxpayer data document (root = `$`). |
| `aggregate` | enum    | no       | `"sum" \| "count" \| "avg" \| "min" \| "max" \| "first" \| "last" \| "join"`. Required when `path` resolves to more than one match (e.g. via `[*]` or a filter) and a single scalar is needed for the box. `"join"` concatenates with `", "` — useful for text boxes (e.g. listing employer names). |
| `transform` | enum    | no       | Optional single post-processing step: `"abs" \| "negate" \| "round"`. Deliberately a small closed set, not arbitrary code. |
| `fallback`  | any     | no       | Value used when the path resolves to nothing (`undefined`/empty array). Default: box is left blank. |

\*\* `path` is omitted only when `literal` is used instead (§6.4).

### 6.1 Path grammar

```
$                         root of the data document
.fieldName                property access
["field name"]            property access (for names with spaces/special chars)
[n]                       array index (0-based)
[*]                       wildcard — all elements of an array
[?(@.field OP value)]     filter predicate over an array; OP ∈ == != > >= < <=
                          value is a JSON literal (string/number/boolean)
```

Segments chain left to right, e.g.:

```
$.dependents[?(@.relationship=='child')][*].ssn
```
→ SSNs of every dependent whose relationship is `"child"`.

A path either resolves to a single scalar (object/string/number/boolean —
used directly) or to a list of matches (whenever it passes through `[*]` or
a filter) — a list **must** be reduced via `aggregate` before formatting;
resolving a box with an unreduced list is a spec violation a
validator/renderer should reject, not silently join.

### 6.2 Why not full JSONPath / JMESPath?

Real JSONPath/JMESPath libraries are a reasonable implementation choice
(and the reference resolver in `src/resolver.ts` accepts this exact
subset), but the spec defines its own minimal grammar rather than adopting
one wholesale so that:
- the surface area an annotator needs to learn is small and tax-form-shaped
  (aggregation is a first-class, explicit field — not a pipe/function
  buried in path syntax),
- any conforming implementation in any language can implement the full
  grammar in well under an hour, keeping the spec genuinely
  format-agnostic rather than "JSON + a specific npm package."

### 6.3 Referencing repeated boxes vs. aggregating into one box

Two different real scenarios are easy to conflate:

1. **One box, many source values** (e.g. 1040 Line 1a = sum of every W-2's
   box 1) → use `aggregate` (§6, above).
2. **Many boxes, one per source item** (e.g. Schedule B Part I lists every
   interest payer on its own line) → use `repeat` (§8) — the box itself
   repeats, each instance binding to one array element.

### 6.4 `literal` boxes

Some boxes aren't sourced from taxpayer data at all (e.g. a form's printed
tax year, or a fixed instructional checkbox). In that case, omit
`dataBinding.path` and provide a static value directly:

```jsonc
"dataBinding": { "literal": "2024" }
```

## 7. `ConditionalSpec` — whether a box renders at all

```jsonc
"conditional": { "showIf": "$.filingStatus == 'marriedFilingJointly'" }
```

`showIf` is a single boolean predicate using the same `@.field OP value`
comparison grammar as path filters (§6.1), evaluated against the data
root. If it evaluates falsy, the renderer skips the box entirely (nothing
drawn — not even a blank/zero). Omit `conditional` for boxes that always
render when their binding resolves.

## 8. `RepeatSpec` — repeating rows

For a line item that repeats once per array element (e.g. one row per W-2,
per dependent, per Schedule B payer), a single annotation acts as a
**template row**:

```jsonc
{
  "id": "schB_interest_row",
  "formLine": "Schedule B Part I",
  "page": 1,
  "position": { "x": 72, "y": 180, "width": 300, "height": 14, "unit": "pt" },
  "format": { "type": "text", "alignment": "left" },
  "dataBinding": { "path": "@.payerName" },
  "repeat": { "over": "$.income.interestPayers[*]", "rowHeight": 16, "maxRows": 4, "overflowFormId": "F1040-SchB-Cont" }
}
```

| Property         | Type    | Notes                                                                              |
|------------------|---------|--------------------------------------------------------------------------------------|
| `over`           | string  | Path resolving to an array; the template repeats once per element.                   |
| `rowHeight`      | number  | Vertical offset (in the box's `unit`) applied per repetition: instance *n*'s `y` = `position.y + n * rowHeight`. |
| `maxRows`        | integer | How many rows physically fit before overflowing the printed area.                    |
| `overflowFormId` | string  | Optional: `formId` of a continuation form/attachment to route rows beyond `maxRows` to. Renderer's responsibility to invoke it; spec just records intent. |

Inside a `repeat` template, `dataBinding.path` is evaluated **relative to
each element** — note the `@.payerName` (current element), not
`$.income.interestPayers[*].payerName` (which would re-select the whole
array from root on every row). `@` as a path root means "current repeat
element"; `$` always means the document root, still usable inside a
repeated row for cross-referencing outside data (e.g. a filing-status flag
that's the same on every row).

## 9. Worked example

See `/examples`:
- `examples/taxpayer-data.json` — a nested taxpayer document (multiple W-2s,
  dependents, filing status).
- `examples/form-1040-page1.annotations.json` — a `FormTemplate` for a
  handful of real 1040 line-1a-style boxes, including a `sum` aggregate and
  a `repeat` row.
- `examples/resolved-output.json` — what a conforming resolver produces:
  a flat list of `{ id, page, x, y, width, height, text, align, fontSize }`
  draw instructions — exactly what a rendering layer (PDF library, canvas,
  SVG, print CSS) needs and nothing more.

Reference resolver: `src/resolver.ts` (+ `src/types.ts` for the type
definitions / "classes" form of this spec). A zero-dependency browser demo
that runs the same logic live against the example data is in `demo/`.

## 10. Validation

`schema/form-annotation.schema.json` is a JSON Schema (draft 2020-12) that
validates the *structural* shape of a `FormTemplate` document (required
fields, enums, types). It cannot validate the path grammar's semantics
(e.g. that a `path` string is well-formed, or that a referenced field
actually exists in some data document) — that's the resolver's job at
resolve time, and a real implementation should surface a clear error
(unresolvable path, list needing aggregate, box exceeding page bounds)
rather than fail silently.

## 11. Explicitly out of scope (v1)

Called out deliberately rather than silently absent:

- **Arithmetic/formula bindings** (e.g. `box = wages - adjustments`
  computed inline). `transform` covers the few unary ops that show up
  constantly (abs/negate/round); anything more belongs upstream, computed
  into the taxpayer data document itself before annotation resolves it —
  keeps the annotation format declarative and auditable rather than a
  hidden second calculation engine.
- **Multi-page flow/pagination logic** beyond `repeat.overflowFormId` —
  deciding *how* to lay out a continuation page is a renderer concern.
- **Font embedding/asset management** — `format.font` is a hint; actual
  font resolution is the renderer's problem.
- **Localization** (non-English forms, non-US locales) — `dateFormat`/
  separators are US-convention defaults only.
- **Signature/image boxes** beyond marking their existence (`type:
  "signature"`) — actual e-signature capture is out of scope for an
  annotation format.

## 12. Future enhancements (would tackle next, given more time)

- A visual annotation authoring tool (drag boxes over a rendered form page,
  emit this JSON) — the format is designed to be easy to *generate*, not
  just hand-write.
- A richer `transform` pipeline (ordered array of ops) once real forms
  demonstrate a genuine need beyond the current unary set, without jumping
  straight to a full formula language.
- Per-field audit metadata (`sourceIrsPublication`, `lastVerified`,
  `verifiedBy`) since tax forms change yearly and annotations silently
  drifting out of date is a real failure mode.
- A `unit test` fixture format — pairs of (taxpayer data, expected resolved
  output) per form, so a form's annotation file can be regression-tested
  the same way code is, independent of any particular renderer.
